# PRD：混合检索升级（BM25 + Vector + RRF）

| 项目         | 内容                                                       |
| ------------ | ---------------------------------------------------------- |
| **产品**     | KnowBase X / KnowFlow                                      |
| **模块**     | `packages/rag-engine` 检索层 + `apps/server` 检索/问答入参 |
| **版本建议** | v1.x（检索能力里程碑）                                     |
| **状态**     | 草案                                                       |

---

## 1. 背景与问题

### 1.1 文档承诺 vs 现状

设计文档写明混合检索为 **BM25（关键词）+ Vector（语义）+ 结果融合（含 RRF 表述）**。

实际代码：

- 仅对向量召回结果做二元词命中加分
- 无独立稀疏检索通路
- 无 BM25 / tsvector 索引
- 无 RRF
- 混合与重排共用 `useReranker`

### 1.2 由此带来的产品问题

| 场景                             | 现象                                              |
| -------------------------------- | ------------------------------------------------- |
| 专有名词、错误码、工单号、函数名 | 向量可能排后或未进 topK，当前无法靠关键词「捞回」 |
| 短查询、精确匹配                 | 语义分不稳定，关键词通路缺失                      |
| 同义改写、自然语言长问           | 向量更优，但缺稀疏通路时无法做真正互补            |
| 打开「重排」                     | 用户以为只是排序更精，实际还偷偷改了召回策略      |
| 中文无空格查询                   | 现有切词几乎失效                                  |

### 1.3 目标表述（一句话）

> 在不替换 pgvector 主存的前提下，补齐「稀疏召回 + 稠密召回 + 可配置融合 + 与重排解耦」的完整混合检索，使行为与文档描述一致，并可用于生产调参。

## 2. 目标与非目标

### 2.1 Goals

1. **双路召回**：Dense（现有 PGVector）与 Sparse（BM25 或等价）独立取候选，再融合
2. **标准融合**：默认支持 RRF；可选线性加权（兼容现有 `denseWeight` 语义并升级其含义）
3. **开关解耦**：`useHybrid` 与 `useReranker` 独立
4. **中英可用**：中文分词/检索至少达到「可用」级别（见功能需求）
5. **可观测**：能看到各通路命中、融合前后分数，便于调参与排障
6. **兼容**：默认行为可配置为与现网接近（纯向量），避免无声破坏

### 2.2 Non-Goals（本 PRD 不做）

- 更换主向量库（Milvus / Qdrant 等）
- 上线商业 Cross-Encoder 云 API 作为必选依赖（bi-encoder 可保留为可选）
- 多模态检索、图谱检索
- 用 Redis 做主检索索引（可用 Redis 做缓存，非本需求核心）
- 一次性重做整条 Agent 编排

## 3. 用户与场景

### 3.1 角色

| 角色                        | 诉求                                     |
| --------------------------- | ---------------------------------------- |
| 知识库使用者（问答/检索页） | 专有名词、条款编号问得出；自然语言也能答 |
| 调参/运营                   | 可调权重、topK、融合方式，并看到效果     |
| 接入方（API）               | 参数稳定、文档与行为一致                 |
| 开发者                      | 实现清晰、可测、可灰度                   |

### 3.2 核心场景

| ID  | 场景                               | 期望                                               |
| --- | ---------------------------------- | -------------------------------------------------- |
| S1  | 查询含产品名/错误码（如 `E-1042`） | 稀疏通路命中原文切片，即使向量分一般也能进最终列表 |
| S2  | 长自然语言问题                     | 稠密通路主导，稀疏补充字面相关段落                 |
| S3  | 仅语义相近、用词完全不同           | 稠密召回，不因无关键词被误伤                       |
| S4  | 关闭 hybrid                        | 与当前纯 `similaritySearch` 行为一致               |
| S5  | 开启 hybrid + rerank               | 先双路融合，再对融合结果重排                       |
| S6  | 文档更新/删除                      | 稀疏索引与向量、元数据一致，无脏命中               |

## 4. 功能需求

### 4.1 检索模式

| 模式      | 说明                  | 是否默认            |
| --------- | --------------------- | ------------------- |
| `vector`  | 仅 dense              | ✅ 是（兼容现网）   |
| `keyword` | 仅 sparse（调试用）   | 否                  |
| `hybrid`  | dense + sparse + 融合 | 否（配置/请求开启） |

**请求参数：**

```typescript
interface SearchParamsV2 {
  topK: number; // 最终返回条数
  minScore?: number; // 模式化阈值，语义见下方说明
  minDenseScore?: number; // 仅 hybrid 模式，过滤 dense 候选，默认 null（不施加）
  retrievalMode: 'vector' | 'keyword' | 'hybrid';
  denseWeight?: number; // 仅 linear 融合时有效，0~1
  fusionMethod?: 'rrf' | 'linear'; // 默认 rrf
  rrfK?: number; // 默认 60
  candidateMultiplier?: number; // 每路候选 = topK × multiplier，默认 3，硬上限 10
  useReranker?: boolean; // 与 retrievalMode 独立
}
```

> **`minScore` 行为分化（必须注意）：**
>
> - `vector` 模式：作用于向量余弦相似度（固定 0~1 范围），默认 0.7
> - `hybrid + rrf` 模式：**默认不启用**。RRF 分数无固定上限，用 0.7 过滤会误杀大量正常结果；如需限制 dense 通路质量，改用 `minDenseScore`
> - `hybrid + linear` 模式：作用于归一化后线性加权分（固定 0~1），语义与 `vector` 一致
> - `keyword` 模式：稀疏分无固定上限，**默认不启用**，如需限制由调用方传 `minSparseScore`（预留字段，暂不实现）
>
> **`minDenseScore`：** 仅在 `retrievalMode=hybrid` 时生效，在 dense 候选阶段过滤低质量结果，默认 null（不施加）。环境变量 `DEFAULT_MIN_DENSE_SCORE=0.3`。

**废弃/迁移：**

- 旧：`useReranker=true` 隐式走「伪混合」
- 新：`useReranker` 只控制重排；混合由 `retrievalMode` 控制
- 过渡期：可保留兼容逻辑并打 deprecation 日志（见 [设计文档 §10](07-hybrid-retrieval-design.md) 迁移计划）

### 4.2 稀疏检索（Sparse）

**必须满足：**

1. 对每个知识库（或全局表 + kbId 过滤）维护可检索的全文索引
2. 查询侧对 user query 做分词/规范化后检索
3. 返回带相关性分数或排序的切片列表（至少能排出相对顺序）
4. 支持 `kbId`（及后续扩展的 `docId`）过滤，与向量侧一致
5. 摄入、删除文档时索引与向量库**同步更新**

**实现路径：**

- 主选：PostgreSQL `tsvector` + `ts_rank` / `ts_rank_cd`
- 中文：`pg_jieba` / `zhparser`，或应用层分词后写入 `to_tsvector('simple', ...)` 的 token 序列
- 备选（不推荐主路径）：应用层 BM25 库

**分数策略：** RRF 路径以排名为主，不强制归一化；linear 路径需固定归一化方式（min-max 或 z-score）。详见 [设计文档 §3–4](07-hybrid-retrieval-design.md)。

### 4.3 稠密检索（Dense）

保持现有 PGVector cosine 通路：`embedQuery` → `similaritySearchVectorWithScore`，`filter: { kbId }`，候选数量 `topK * candidateMultiplier`（hybrid 时）。

### 4.4 融合（Fusion）

**默认 RRF：**

$$\mathrm{RRF}(d) = \sum_{r \in R} \frac{1}{k + \mathrm{rank}_r(d)}$$

$R$ = {dense, sparse}，rank 从 1 开始，未出现则该项为 0，$k$ 默认 60。

**可选 Linear：**

$$s = w \cdot s_{\mathrm{dense}} + (1-w) \cdot s_{\mathrm{sparse}}$$

仅出现在一路的文档，另一路视为 0（详见设计文档）。

### 4.5 重排（Rerank）

- 输入：融合后的列表（或 vector-only 列表）
- 现有 bi-encoder 继续作为默认实现
- **不得再偷偷切换召回模式**
- Cross-Encoder 作为后续 epic，不在本 PRD 必选范围

### 4.6 摄入与一致性

| 操作     | Dense                | Sparse           |
| -------- | -------------------- | ---------------- |
| 摄入     | 成功写 PGVector      | 写/更新全文索引  |
| 删除文档 | 删向量行             | 删对应全文行     |
| 失败     | 回滚，两边不留半成品 | 至少提供补偿任务 |

切片元数据仍在现有 chunks 表；稀疏索引表结构选型（A/B 方案）详见设计文档。要求可按 kbId/docId 批量删除。

### 4.7 可观测性

debug 或管理端可选返回各通路命中明细（字段结构见设计文档 §7）。生产默认可不返回，`debug=true` 或内部 header 打开。

## 6. 指标与成功标准

### 6.1 离线（发布前）

固定评测集（≥ 50 query，覆盖专有名词、短词、长问、中英混合）：

| 指标                 | 目标（相对当前纯向量基线）                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| 专有名词类 Recall@10 | **+15%** 或绝对 ≥ 0.9                                                                        |
| 语义改写类 Recall@10 | 不低于基线 -5%                                                                               |
| 整体 nDCG@10         | 不低于基线，目标 +5%                                                                         |
| 延迟                 | hybrid P95 相对纯向量模式增幅 **< 50ms**（仅计算召回+融合耗时，**不含** embedding 网络调用） |

### 6.2 在线（灰度后）

- 检索无结果率、人工点踩率、问答「无依据胡编」投诉
- 稀疏/稠密空结果比例监控

### 6.3 功能验收清单

- [ ] `retrievalMode=vector` 与升级前纯向量结果一致（同 seed 数据）
- [ ] `keyword` 能命中仅字面相关、向量分很低的切片
- [ ] `hybrid + RRF` 能同时提升 S1 且不显著伤害 S3
- [ ] 删除文档后两路均不可再命中
- [ ] `useReranker` 不再改变召回模式
- [ ] 中文无空格 query 有合理命中（case 集通过）
- [ ] API 文档与 OpenAPI/前端类型同步

## 8. 风险与缓解

| 风险                                 | 影响       | 缓解                                                      |
| ------------------------------------ | ---------- | --------------------------------------------------------- |
| 中文分词扩展部署复杂                 | 稀疏质量差 | 提供「应用层分词 + simple 词典」降级；Docker 镜像预装扩展 |
| RRF 与旧 `minScore` 混用，结果被误杀 | 召回量骤降 | 模式化阈值策略；默认 hybrid 不用 0.7 卡 RRF 分            |
| 摄入双写失败，索引不一致             | 脏数据     | 事务或 outbox；启动校验任务                               |
| 延迟上升                             | 体验下降   | 并行召回、限制候选倍数、可选缓存 query→结果               |
| 默认改 hybrid 导致行为突变           | 客诉       | 默认保持 vector；文档与 UI 引导开启                       |
| 文档与代码再次漂移                   | 信任下降   | PR 强制更新 design doc；单测锁定公式                      |

## 9. 依赖与假设

- 继续使用 PostgreSQL + pgvector
- 允许 DB 迁移（加列/扩展）
- Embedding / LLM 接口不变
- 不强制上 Redis；缓存为可选优化
- Agent 编排仍调用同一 `retrieve` / `retrieveAndChat`，自动受益

## 10. 决策摘要（均已拍板，详见 [设计文档 §3 / §8.2](07-hybrid-retrieval-design.md)）

| #   | 问题                            | 结论                                                                             |
| --- | ------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 中文分词策略                    | 应用层 jieba 分词 + `to_tsvector('simple', ...)`；不依赖 zhparser/pg_jieba 扩展  |
| 2   | 稀疏索引位置                    | 挂 `chunks` 表（不在 `langchainjs` 上加列）                                      |
| 3   | `langchainjs.id` vs `chunks.id` | 不是同一 UUID，sparse-store 通过 `docId` 反向关联                                |
| 4   | `minDenseScore` 是否引入        | 要，仅 hybrid 模式，过滤 dense 候选，默认 0.3                                    |
| 5   | 评测集维护与 CI                 | 仓库内 golden set（`__tests__/fixtures/eval-queries.json`）+ CI 冒烟；人工集外置 |

## 11. 总结（给评审）

本 PRD 要解决的不是「再加一点关键词加分」，而是把检索做成文档所描述的形态：

- **两路真正召回**（向量 + BM25/全文）
- **可解释融合**（默认 RRF）
- **与重排解耦**
- **摄入一致、可测、可灰度、默认可兼容现网**

落地后，「混合检索」一词在产品、文档、代码三者中的含义才一致；专有名词与语义问句可以同时被系统覆盖，而不是互相挤占唯一的 topK 名额。
